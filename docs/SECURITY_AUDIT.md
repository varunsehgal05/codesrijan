# CodeSrijan security and paid registration audit

Assessment date: 23 October 2026. Local source review only; no deployment, production database mutation, real payment, or email dispatch was performed by this audit. Line numbers may shift as parallel fixes land; route names below identify the relevant implementation.

## Verified and fixed locally

- **Critical — MongoDB production credential embedded in source.** server/server.js, server/check_user.js, server/test_phase2_security.mjs, and server/test_phase3_paid_hackathons.mjs contained credential-bearing connection fallbacks. Removed these fallbacks. Runtime now requires MONGO_URI. Test scripts require TEST_MONGO_URI pointing to an explicit local test database; production database names, remote hosts, SRV, credentials, and URI query options are rejected by server/test-database.js. Phase 2 dynamically imports the server only after setting the isolated URI/database name. Merely setting NODE_ENV=test previously did not isolate the database.
- **Critical — fixed administrative credentials reinstalled at each boot.** server/server.js reset existing admin/student passwords to source literals and promoted an E2E address to administrator. Removed that behavior. Optional SEED_ADMIN_PASSWORD/SEED_STUDENT_PASSWORD only create absent seed identities and require at least 12 characters. Admin user creation also requires an explicit password instead of a universal fallback. Existing production passwords are unchanged by these local edits and require rotation through an authorized account-management flow.
- **Critical — passwordless local login for Firebase-only identities.** POST /api/auth/login skipped bcrypt when passwordHash was absent. It now denies local login for those identities.
- **Critical — Firebase email-prefix privilege assignment.** server/middleware/auth.js assigned administrator to newly provisioned users whose email began with an admin prefix. All new Firebase and local email/password identities now start as student. Firebase claims must indicate verified email, and active/verified account state is enforced. Existing roles are not silently rewritten.
- **High — password hashes included in user responses.** GET /api/users and other queries excluded a nonexistent password field rather than passwordHash; login and /auth/me serialized complete user documents. Corrected projections and added schema-level JSON removal of passwordHash, retaining internal access for bcrypt.
- **High — disabled accounts accepted via sessions/Firebase.** Middleware previously rejected only suspended legacy accounts and did not enforce the same check for Firebase. Both paths now require active and email-verified identities.
- **Deployment policy — unsafe override enabled.** vercel.json explicitly enabled DANGEROUSLY_DEPLOY_VULNERABLE_TANSTACK_START_XSS in runtime and build environments. Removed both overrides. This does not establish dependency safety; the hosting platform may correctly reject the current dependency version and require an upgrade before deployment.

## Remaining findings requiring follow-up

1. **High — paid roster consistency and fee count.** Team creation initializes memberIds with the leader; registration previously used memberIds.length + 1. This double counts a normal leader when calculating per-participant fees and size bounds. Registration also queries members with $in without checking that every referenced identity exists. Fixed locally in the parallel payment workstream: IDs are deduplicated, the fee uses the unique count, and missing member documents are rejected.
2. **High — roster locks are incomplete.** POST /api/teams/leave, DELETE /api/teams/:id, and POST /api/teams/:id/transfer previously lacked registration-lock checks. Fixed locally: these sibling routes now also reject locked teams, with focused regression coverage. GET registration uses a saved roster snapshot, so team and registration membership can diverge.
3. **High — OTP attempts and token consumption are read-then-save.** /api/auth/verify-email loads a document, compares bcrypt, then saves attempts/usedAt. Concurrent requests can lose failed-attempt increments or consume one OTP twice. The comment claiming atomic increment does not match the implementation. Fixed locally with conditional atomic token consumption, bounded $inc attempts and token-hash matching so concurrent replacement invalidates stale requests. Activation also requires pending_verification, preventing reactivation of disabled accounts. Reset-token consumption remains a separate follow-up.
4. **High — resend resets lockout state.** /api/auth/resend-otp deletes the verification record and creates one with attempts=0. The per-record 60-second resend cooldown does not impose a cumulative account/IP send budget. Pending-registration recovery also issues fresh codes. Fixed account-level resend and recovery paths locally: update the same verification record, preserve attempts, enforce lockout/cooldown, and cap sends at five per hour. Conditional matching prevents concurrent resends from both succeeding. Responses retain retryAfter. A distributed IP-level budget remains a follow-up.
5. **High — payment review permits arbitrary state changes.** POST /api/admin/payments/:registrationId/review can approve pending_proof without proof or reverse a previously verified record. It lacks a source-state predicate or conditional atomic update. Fixed locally with one conditional findOneAndUpdate requiring payment_under_review, receipt and transaction reference; competing reviewers produce one winner and one409 without duplicate history.
6. **Medium — receipt size contract differs from request parser.** express.json() has its default approximately 100 KB body limit while payment proof validation permits approximately 5 MB. The UI reads images as data URLs; ordinary images can fail before the handler. Raise a narrowly scoped parser limit and validate actual media bytes/type, or use private object storage.
7. **Medium — receipt privacy depends on external URLs.** The dedicated receipt endpoint is authenticated and admin-only. The proof itself may be an arbitrary HTTP(S) URL, and full registration responses include its URL and roster email addresses for the owner/roster and administrators. This does not make externally hosted files private. Prefer private storage and short-lived authorized access; document roster-member receipt visibility.
8. **Medium — unauthenticated socket room subscription.** Socket.IO connection handlers accept any conversation:join ID without authenticating or checking membership. Assess all room broadcasts; room IDs must not serve as authorization.
9. **Medium — draft visibility trusts header presence.** GET /api/hackathons/:id checks only that an Authorization header exists for draft visibility rather than verifying an administrator session.
